# txt AIエージェント接続 設計書

- 対象: txt（`https://txt.2-38.com/`、repo `kandotrun/txt`）への AI エージェント接続機能の追加設計
- 位置付け: 仕様 `spec.md`（当時 仕様版 1.3、Web-only）への改定として設計し、**フェーズ1（読み取り）・フェーズ2（書き込み）を 2026-10-25 に実装し本番反映済み**。改定内容は仕様版 1.4 に取り込み済み（§11）。本書は設計の記録として残す
- 決定済み事項（2026-10-25、Kan）:
  - AIエージェント（Muse等）が既存の1枚メモを**読み書き両方**できるようにする
  - 復号はエージェント側（KanのMac上のローカルMCPサーバー）でのみ行い、サーバーに平文・鍵を渡さない
  - MCPサーバーへの接続は Tailscale 経由のみとし、T3 Code MCP と同じ運用パターン（tailnet限定・期限付きトークン・ペアリング承認）にする
  - エージェントごとに個別の鍵ラップとトークンを持ち、個別に失効可能にする
  - **復旧キーをエージェントに渡す案は禁止**（復旧キーは実質マスター鍵の共有になるため）

---

## 1. 目的・非目的、前提

### 1.1 目的

利用者本人のAIエージェントが、本人のアカウントの1枚メモに対して次を行えるようにする。

1. 現在の本文を平文で読む（メディアは §8 のコピー用 Plaintext 表現に倣い `[画像: ファイル名]` 等のプレースホルダーで表す）
2. 既存の保存プロトコル（ETag CAS）を守って本文へ追記・置換する
3. 利用者がWebのセキュリティ設定から、エージェントごとに登録・失効・状態確認ができる

### 1.2 非目的

- サーバー側での本文復号、検索、要約、その他いかなる平文処理（現行 §1 で不採用とされた「Worker側の本文復号」を復活させない）
- エージェントによるメディアのアップロード・削除（フェーズ2までは対象外。§9.3、§12 参照）
- エージェントによるパスキー管理、復旧キー操作、アカウント削除等の機密操作（§7.3 で API スコープから除外する）
- 複数文書、履歴、共有など現行 §19 の対象外事項の追加（エージェント接続のために文書モデルを変えない）
- 一般公開機能としてのエージェント接続の即時提供（初期はフラグ付き・対象アカウント限定を想定。§12 未決事項1）

### 1.3 前提（現行 spec の該当節）

本設計は現行 spec の次の契約を**変更せずに土台として使う**。

| 前提 | spec の根拠 |
| --- | --- |
| サーバーは平文本文・ファイル名・MIME・PRF出力・VaultKey・fileKey を受け取らない | §6.5 |
| VaultKey は独立した32バイト乱数で、入口ごとに別々にラップされる（パスキー複数本・復旧キーが同じ VaultKey を包む） | §6.1、§6.2、§7.1 |
| 鍵ラップは `Encode`（uint32 BE 長さ前置）+ HKDF-SHA256 + AES-256-GCM（nonce 12B、タグ16B、base64url）でバイト単位に固定される | §6.2、§6.3 |
| 本文暗号化は `snapshotKey = HKDF-SHA256(VaultKey, mutationId, Encode("txt/v1/document-key", accountId, documentId, keyVersion))`、AAD に accountId/documentId/mutationId/encryptedRevision を含む | §6.3 |
| 本文の保存形式は共通文書モデル（text/media ブロックの JSON 全体を暗号化）であり、ProseMirror JSON や HTML を通信形式にしない | §8 |
| 保存は ETag（`"d-<documentId>-e-<syncEpoch>-r<revision>"`）による CAS が必須で、`If-Match: *` と Last Write Wins は禁止。同じ mutationId の同じペイロード再送は冪等、異なるペイロードは 409、古い ETag は 412 | §10.2、§10.3、§12.2 |
| セッションは 256bit 以上の不透明トークンで、D1 には SHA-256 ハッシュだけを保存する。失効は account の `auth_epoch` と連動する | §5.4、§12.1 |
| 機密操作は5分以内の step-up 再認証を要求する | §5.4、§7 |
| 運用ログに本文・鍵・トークン類を記録しない | §14 |
| パスキー追加は「解除 + step-up → ラップ作成 → 試験復号 → 有効化」の順序を踏み、試験前に既存の唯一の入口を消さない | §7 |

一方で、次の現行条文はエージェント接続と直接衝突するため、**改定が必要**である（詳細は §11）。

- §5.4「セッションはCookie認証のみとし、Bearer認証は受け付けず」→ Webセッションについての条文として維持し、エージェント専用トークンだけを例外として切り分ける（§5）
- §19 の対象外一覧にある「AI」→ エージェント接続を対象外から外す
- §2「ネイティブアプリは提供・開発しない」→ 利用者向けアプリではなくローカルブリッジである MCP サーバーを例外として明記する

## 2. 脅威モデルと守る境界

### 2.1 資産

- 本文平文とメディア平文（fileKey を含む共通文書モデル全体）
- VaultKey（漏れると現在の本文・添付のすべてが復号可能になる）
- エージェント秘密鍵（VaultKey のラップを解ける唯一の材料。トークンとセットで本文アクセス権そのもの）
- エージェントトークン（暗号文の取得・更新の認可）
- 復旧キーとパスキー PRF 出力（**エージェントには一切渡らない**ことを設計で保証する）

### 2.2 脅威と対策

| 脅威 | 影響 | 対策 |
| --- | --- | --- |
| サーバー / Cloudflare の侵害・内部閲覧 | 暗号文、鍵ラップ、メタデータ（§6.5 でサーバーに見える範囲）の漏洩 | 平文・VaultKey は従来どおりサーバーに存在しない。エージェント追加でもこの性質を変えない（ラップ済み鍵と暗号文のみ） |
| ネットワーク盗聴 | 暗号文とトークンの漏洩 | TLS（既存）+ MCP 接続は Tailscale（WireGuard）内のみ。トークンはハッシュ化して保存し、平文は発行時の1回だけ |
| エージェントトークンのみ漏洩 | 暗号文の取得・（write scope があれば）暗号文の上書きはできるが**復号はできない** | トークンと秘密鍵を分離する本設計の要点。ただし悪意ある暗号文上書き（本文の破壊）は可能なので、write トークンの漏洩時は §9.5 のローカルバックアップからの復旧手順を使う |
| Mac 上の MCP サーバー / 秘密鍵の侵害 | VaultKey を復号でき、本文・添付の全平文が漏れる。**最も重大な侵害** | 秘密鍵は Keychain 保管（§8.2）。エージェントごとに鍵を分けるため、侵害されたエージェントの失効で API アクセスは止められる。ただし下記 §2.3 のとおり、既に取得された VaultKey 自体は失効では無効化できない |
| Muse 等の MCP クライアント側の侵害・誤動作 | MCP 経由で読めた平文の漏洩、意図しない書き込み | MCP サーバーは Kan の Mac 上に閉じ、MCP 自体にも T3 Code と同方式のペアリング＋期限付きアクセストークンを要求する（§8.1）。書き込みは §9 の安全策（追記優先・置換承認制・競合時停止）で被害を限定する |
| メモ本文中のプロンプトインジェクション | エージェントが本文中の指示文に誘導され、想定外の読み書きを行う | MCP サーバー側では防げない（モデルの振る舞いの問題）。緩和策として、書き込みツールの承認制（§9.2）と監査ログ（§8.5）で事後検出可能にする。運用上も「本文はデータであり指示ではない」前提をエージェント側プロンプトに明記する |
| 登録フローへの割り込み（偽エージェントの公開鍵を差し込む） | 攻撃者の鍵で VaultKey がラップされ、本文が漏れる | 登録は解錠 + step-up 済みブラウザー内でのみ開始でき、公開鍵フィンガープリントの双方向確認と試験復号を有効化の必須条件にする（§4.3） |
| ブラウザー側の XSS・配信 JS の侵害 | 既存の脅威（§6.5）と同じ。エージェント登録画面も同じ前提に乗る | 既存 CSP（§14）を維持し、登録画面に外部スクリプトを足さない |

### 2.3 守る境界と、失効の限界

守る境界は次の1線である。

> **平文と VaultKey が存在してよい場所は、利用者本人の端末（ブラウザーのメモリー内）と、本人が登録したエージェントの MCP サーバー（Mac のメモリー内）だけ。サーバー、Cloudflare、ネットワーク上には暗号文とラップ済み鍵しか流れない。**

現行 §6.1 がパスキーについて述べている注意はエージェントにもそのまま当てはまる。

- **入口の失効 ≠ 既にコピーされた VaultKey の失効。** エージェントを失効させると、そのエージェントのトークンは即時に無効化され、以後の暗号文取得・更新は止まる。しかし侵害時に VaultKey を既に抜かれていた場合、攻撃者は手元の暗号文コピーを引き続き復号できる。
- エージェント侵害が疑われる場合の完全な回復は **VaultKey ローテーション**である。新 VaultKey を生成し、本文を再暗号化し、全入口（パスキー全本・復旧キー・エージェント全件）のラップを作り直す（§10 フェーズ3）。
- さらに注意: 共通文書モデル内の fileKey は VaultKey の下にあるため、VaultKey ローテーションだけでは「既に平文の文書モデルを取得済みの攻撃者」に対してメディア暗号文の復号を止められない。メディアまで含めた完全な再暗号化（新 fileKey + 再アップロード）が必要になるケースがあることを、ローテーション手順書に明記する。

## 3. 全体アーキテクチャ

```text
┌──────────────────────── Kan の Mac ────────────────────────┐
│                                                            │
│  ブラウザー (Safari 等)          MCP サーバー (常駐)        │
│  ┌──────────────────┐           ┌────────────────────────┐ │
│  │ txt Web          │           │ P-256 秘密鍵           │ │
│  │ ・解錠 (PRF)     │  登録時   │   → macOS Keychain     │ │
│  │ ・step-up        │ ◀──────── │ VaultKey               │ │
│  │ ・VaultKey を    │  公開鍵と │   → メモリー内のみ     │ │
│  │   エージェント   │  フィンガ │ 復号・暗号化 (§6.3流用)│ │
│  │   公開鍵でラップ │  ープリント│ CAS クライアント (§10) │ │
│  └────────┬─────────┘           └───────┬────────────────┘ │
│           │                             ▲                  │
└───────────┼─────────────────────────────┼──────────────────┘
            │ HTTPS (Cookie, 既存)        │ MCP over Tailscale のみ
            │                             │ (Muse が接続、T3 Code と同方式)
            ▼                             │
┌──────────────────────────────┐   ┌──────┴───────┐
│ Cloudflare Workers + Hono    │   │ Muse /      │
│ ・既存 Web API               │   │ Claude Code  │
│ ・エージェント管理 API (新設)│   │ 等のエージェント│
│ ・/document は既存契約を流用 │   └──────────────┘
│ D1: agent_keys / agent_tokens│
│     documents (暗号文のみ)   │
│ R2: 暗号化添付               │
└──────────────────────────────┘
            ▲
            │ HTTPS (Bearer: エージェントトークン、新設)
            │ MCP サーバーが暗号文を取得・更新する
   (MCP サーバー ──► Worker の経路は上図ブラウザーと同じ Worker へ)
```

要点:

- 復号・暗号化のコードは新規に作らず、`packages/protocol`（Encode、HKDF/AES-GCM 契約、共通文書モデル、テストベクトル）を MCP サーバーからも使う。暗号契約の実装を2系統にしない。
- Worker の変更は「エージェントの登録・ラップ配布・トークン認可」の追加に限る。本文処理ロジック（CAS、参照検証、清掃）は既存の `/document` 実装をそのまま使う。
- MCP サーバーは Mac の Tailscale インターフェースだけに bind し、公開インターネットや LAN へは公開しない。

## 4. 鍵ラップ方式

### 4.1 方式選定

パスキーのラップは PRF 出力という対称秘密を KEK に使う方式（§6.2）だが、エージェントには PRF を実行する認証器がない。代わりに**非対称鍵ペア**を使う。

- エージェント（MCP サーバー）が P-256 鍵ペアを生成し、秘密鍵は Mac の Keychain から出ない
- 登録時、ブラウザーが一時 P-256 鍵ペアを生成し、ECDH で共有秘密を作り、HKDF で KEK を導出して VaultKey をラップする（ECIES 型）
- サーバーが保存するのは、既存 `key_envelopes` と同じ形の「salt / nonce / ラップ済み鍵」と、ブラウザーの一時公開鍵

P-256 を選ぶ理由: Web Crypto（§6.3 の基盤）がブラウザーと Node の双方で ECDH P-256 + HKDF + AES-GCM を標準サポートし、X25519 はブラウザー側の対応が環境依存で §13 の互換性方針（実測するまで対応済みにしない）と衝突するため。秘密鍵を Secure Enclave に置く将来案（§12）でも P-256 が前提になる。

### 4.2 導出式（既存 §6.2 の形式に倣う）

```text
agentId        = UUID (登録時にサーバーが発行)
agentKeyPair   = P-256 鍵ペア (MCP サーバーが生成、秘密鍵は Keychain)
ephKeyPair     = P-256 一時鍵ペア (ブラウザーがラップのたびに生成、使い捨て)

sharedSecret   = ECDH(ephPriv, agentPub) の生出力 32 バイト
                 (Web Crypto deriveBits(256))
wrapSalt       = 乱数 32 バイト (ラップごとに新規、サーバー保存)
KEK-agent      = HKDF-SHA256(sharedSecret, wrapSalt,
                 Encode("txt/v1/agent-wrap", accountId, agentId), 32)
wrapAAD        = Encode("txt/v1/agent-vault-key", formatVersion, keyVersion,
                 accountId, agentId)
wrappedVaultKey = AES-256-GCM(KEK-agent, randomNonce12, VaultKey, wrapAAD)
```

保存するもの: `agentId`、`agentPub`（非圧縮点 65 バイト、base64url）、`ephPub`（同）、`wrapSalt32`、`nonce12`、`wrappedVaultKey`、format/key_version。
保存しないもの: `ephPriv`（ブラウザーのメモリー内でもラップ直後に破棄）、`sharedSecret`、`KEK-agent`、VaultKey。

解除（MCP サーバー側）は対称である: `sharedSecret = ECDH(agentPriv, ephPub)` から同じ導出を行い、AES-GCM のタグ検証に成功した場合だけ VaultKey を得る。タグ検証失敗は「鍵不足・改変」と同じ扱いとし、空文書へのフォールバックはしない（§6.3 の既存原則）。

ドメイン分離文字列（`txt/v1/agent-wrap`、`txt/v1/agent-vault-key`）はパスキー用（`txt/v1/passkey-wrap`、`txt/v1/vault-key`）および復旧用（`txt/v1/recovery-*`）と重ならない。`Encode` の表現規則（UUID は16バイト、整数は uint64 BE 等）は §6.3 をそのまま適用する。

### 4.3 登録フロー

パスキー追加（§7）の手順構成を踏襲する。

1. 利用者は Web の「その他 → セキュリティ設定」で「エージェントを追加」を開く。**解錠済み + 5分以内の step-up** が前提（§5.4）。
2. ブラウザーが登録セッションを作成する: サーバーは `agentId`（仮発行）と10分期限のペアリングコード（128bit 乱数、D1 には SHA-256 ハッシュのみ保存。`challenges` テーブルの purpose 拡張で扱う）を返す。
3. 利用者は Mac のターミナルで `txt-agent enroll` を実行し、ペアリングコードを入力する。MCP サーバーは P-256 鍵ペアを生成して秘密鍵を Keychain に保存し、公開鍵とエージェント表示名（例: `Clio (Mac)`、平文の個人情報を含めない）を登録セッションへ送信する。
4. ブラウザーは公開鍵の**フィンガープリント**（`SHA-256(agentPub)` の先頭を人が比較できる形式で表示）を出し、MCP 側ターミナルも同じフィンガープリントを表示する。利用者が一致を確認した場合だけ次へ進む。
5. ブラウザーが §4.2 の手順で VaultKey をラップし、ラップ一式をサーバーへ保存する（この時点では `pending`）。
6. **試験復号**: ブラウザーは検証用カナリアを作る。`canaryKey = HKDF-SHA256(VaultKey, agentId, UTF8("txt/v1/agent-canary"), 32)` で乱数16バイトを AES-GCM 暗号化したものと、`SHA256(canary平文)` をサーバーに置く。MCP サーバーはラップを解除してカナリアを復号し、平文を登録セッション経由で返す。サーバーがハッシュ一致を確認できた場合だけ `active` にする。カナリア平文そのものは秘密情報ではない（乱数）ため、この往復で VaultKey は漏れない。
7. 有効化と同時に、利用者はトークン発行へ進む（§5.3）。トークン発行まではエージェントは文書 API を呼べない。
8. 失敗・期限切れの登録セッションは24時間を目安に清掃する（§5.3 の pending 清掃と同じ扱い）。試験に失敗した状態で既存の入口（パスキー、復旧キー、既存エージェント）に変更は加えない。

再ラップ（後述のローテーションや鍵ペア再生成時）も同じフローを使い、`key_version` またはラップ世代を上げて旧ラップと置換する。

## 5. 認証: エージェント専用トークン

### 5.1 方針と比較

エージェントはブラウザーではないため Cookie セッション（§5.4）を使えない。次の2案を比較した。

| 案 | 内容 | 長所 | 短所 |
| --- | --- | --- | --- |
| A. `sessions` テーブル拡張 | `client_kind = 'agent'`、`scope = 'agent:read'` 等として既存セッション基盤に相乗り | 実装が小さい。期限・失効・`auth_epoch` の仕組みをそのまま使える | セッション一覧（§12.2 `GET /sessions`）にエージェントが混ざり、Web セッションの管理 UI と意味がずれる。トークンと鍵（agentId）の対応が弱く、エージェント単位の失効が表現しにくい |
| B. `agent_tokens` 新テーブル（**推奨**） | エージェント専用テーブルを新設し、`agent_id` 外部キー、scope、期限、最終利用時刻を持つ。認可判定は既存セッションと同じ規則（ハッシュ保存、`auth_epoch` 照合）を共有コードで実装 | エージェント単位の失効・棚卸しが素直。Web セッションの意味を汚さない。将来の scope 拡張（メディア等）にも耐える | テーブルと認可コードの追加分だけ実装が増える |

**推奨は B**。ただし認可の規則そのものは §5.4 のセッション契約（256bit 不透明トークン、D1 には SHA-256 ハッシュのみ、失効と `auth_epoch` をサーバーで確認）を複製ではなく共通化して使う。

### 5.2 現行 spec「Bearer 禁止」との整合（spec 改定点）

§5.4 の「Bearer認証は受け付けず」は **Web セッションに関する条文**として維持し、次を改定で明示する。

- `Authorization: Bearer` を受け付けるのは、エージェントトークンで認可される経路（§7.2 の一覧）だけとする
- Web の Cookie セッションを Bearer で提示しても認可しない（現行どおり）。逆にエージェントトークンを Cookie で提示しても認可しない
- エージェント経路では Origin / `X-Txt-Request` による CSRF 検証は適用しない（ブラウザー外クライアントのため）。代わりにトークン必須 + レート制限（§14 の認証失敗制限と同じ枠組み）を適用する
- 1つのリクエストに Cookie と Bearer の両方があっても曖昧に扱わず、エージェント経路では Bearer のみ、Web 経路では Cookie のみを評価する

### 5.3 トークンの仕様

- 形式: 256bit 乱数の不透明トークン。平文は発行時に1回だけ表示し、利用者が MCP サーバーの設定（Keychain）へ登録する。D1 には `SHA-256(トークン)` のみ保存する。接頭辞 `txta1.` を付け、漏洩検出と取り違え防止に使う（秘密強度は乱数部分が担う）
- scope: `agent:read`（ラップ取得、文書取得、メディア暗号文取得）と `agent:write`（文書更新。read を含む）を分ける。既定の発行は `agent:read` のみとし、write は利用者が登録画面で明示的に有効化した場合だけ付ける
- 期限: **絶対期限30日**、無操作期限は設けない（エージェントは間欠的に動くため無操作失効と相性が悪い。代わりに絶対期限で区切る）。T3 Code のアクセストークン（30日）と運用リズムを揃える
- 更新: 期限切れ前に、MCP サーバーがエージェント秘密鍵による ECDSA 署名（サーバー発行の challenge への署名）で鍵所持を証明し、新トークンの発行を受ける。秘密鍵を失った場合はこの経路を使えず、§4.3 の登録からやり直す。署名更新はフェーズ3で提供し、フェーズ1〜2 は Web 画面からの再発行（旧トークンは即時失効）で代替する
- 失効: 次のいずれかで即時無効化する
  - 利用者が Web のセキュリティ設定で当該エージェントまたは当該トークンを失効させたとき（`revoked_at` を立て、以後の認可は 401）
  - 対応する `agent_keys` 行が失効したとき（従属する全トークンも失効）
  - アカウントの `auth_epoch` が上がったとき（復旧確定 §7.2、アカウント削除 §15 と連動。トークン行に発行時 `auth_epoch` を保持し、認可時に照合する）
- エージェントトークンでは呼べないもの: パスキー管理、復旧、エージェント管理、アカウント削除、セッション管理。scope 違いは 403、トークン無効は 401、他人の ID は存在を漏らさず 404（§12.2 の既存規則どおり）
- レート制限: トークン単位とアカウント単位の二重で、文書取得・更新の頻度上限を設ける。超過は 429 + `Retry-After`（§10.6 の既存扱いに合わせる）

| --- | --- | --- |
| GET /agent/envelope | agent:read | 自分（トークンの agentId）の鍵ラップ一式を取得。他エージェントのラップは引けない（トークンから agentId を決め、クライアント指定を受け付けない。§12.2「所有者はセッションから決める」と同じ原則） |

## 8. MCP サーバー設計（Mac 常駐）

### 8.1 配置と接続

- 実装場所: repo 内 `apps/agent/`（Node / TypeScript）。`packages/protocol` を直接 import し、暗号契約と共通文書モデルの検証を Web と共有する。新規に暗号コードを書かない
- 常駐: launchd ユーザーエージェントとして Mac に常駐。再起動時はロック状態で起動し、初回ツール呼び出し時に解除する（パスキーの都度入力は求めない。秘密鍵 + トークンが揃っていれば解除できるのがエージェント接続の前提であり、その分 Keychain の ACL で守る）
- 待ち受け: Mac の Tailscale インターフェース（100.x アドレス）のみに bind する専用ポート。`0.0.0.0` には bind しない
- Muse からの接続: T3 Code MCP と同じ方式。ペアリングコードによる承認 + 期限付きアクセストークン（MCP 専用、txt のエージェントトークンとは別物）。この2つを混同しない: MCP アクセストークンは「誰が MCP を叩けるか」、txt エージェントトークンは「MCP が txt API を叩けるか」
- 同時接続: MCP クライアントは複数（Muse、Claude Code 等）を許可するが、書き込みはサーバー内部で直列化する（§8.4）

### 8.2 鍵とトークンの保管

| 対象 | 保管先 | 備考 |
| --- | --- | --- |
| P-256 秘密鍵 | macOS Keychain（当該ユーザー、当該バイナリのみアクセス可能な ACL） | ファイル平文保管は禁止。書き出し API を作らない |
| txt エージェントトークン | macOS Keychain | 設定ファイルには token_id と期限だけを平文で持ってよい |
| MCP アクセストークン（ハッシュ） | MCP サーバーの状態ファイル | T3 Code と同様、平文はクライアント側が保持 |
| VaultKey | プロセスメモリー内のみ | ディスク、swap を意図的に使わない。ロック操作とプロセス終了で破棄 |
| 復号した本文 | プロセスメモリー内のみ | キャッシュは最新 revision の1世代だけ。永続キャッシュを作らない（書き込み前のローカルバックアップは暗号文で持つ。§9.5） |

解除フロー（MCP サーバー起動後・初回呼び出し時）: エージェントトークンで `GET /agent/envelope` → Keychain の秘密鍵で §4.2 の逆手順を実行 → VaultKey をメモリーに保持。以後の読み書きは §6.3 の契約どおり `snapshotKey` を mutationId ごとに導出する。

### 8.3 ツール一覧

すべて対象は本人の1枚メモのみ。文書を指定する引数は持たない（accountId/documentId はトークンと取得結果から決める）。

| ツール | 引数 | 返り値 | 説明 |
| --- | --- | --- | --- |
| `txt_status` | なし | revision、updatedAt、エージェント表示名、トークン残り期限、ロック状態 | 本文を含まない状態確認 |
| `txt_read` | なし | 平文テキスト（メディアは §8 のコピー表現で `[画像: 名前]` 等）、ETag、revision | 全文取得。取得のたびにサーバーへ条件付き GET し、キャッシュを正としない |
| `txt_append` | `text`（追記する文字列） | 新 revision、新 ETag | 末尾 text ブロックへの追記（§9.1）。書き込み系の既定ツール |
| `txt_replace` | `block_id`、`expected_text`（置換前の完全なブロック文字列）、`new_text`、`confirm: true` | 新 revision、新 ETag | ブロック単位の置換。承認制（§9.2）。`expected_text` が現在のブロックと一致しない場合は書かずに現在の内容を返す |
| `txt_search_replace` | `find`、`replacement`、`confirm: true` | 新 revision、新 ETag | 全文から `find` を探す置換は、一致が**ちょうど1件**のときだけ実行する。0件・複数件では書かずに件数と該当ブロック ID を返す（§9.2） |

メディアの追加・削除、ブロックの削除、文書全体の置換ツールはフェーズ2までに**作らない**。必要になった場合は別途設計する。

### 8.4 書き込みの内部手順（全書き込みツール共通）

書き込みは共通文書モデル（§8）への**ブロック操作**として定義し、平文文字列の単純な結合で済ませない。

1. `GET /document` で最新の暗号文と ETag を取得し、復号して共通モデルを得る
2. モデルの妥当性を検証する（§8 の規則: 未知ブロック型を落とさない、media 辞書と参照の整合、`referencedMediaIds` と復号モデルの集合一致。不一致なら書かずにエラー）
3. 操作をモデルへ適用する（ブロック ID の規則は §8: 通常編集で ID を再生成しない。追記の対象ブロック選定は §9.1）
4. 新しい mutationId を発行し、`encryptedRevision = revision + 1` として §6.3 の契約で暗号化する
5. 送信ペイロード（mutationId、暗号文、参照集合）を**送信前にローカルへ記録**する（冪等再送用。§9.4）
6. `PUT /document` を `If-Match: <ETag>` で送る。成功したら新 ETag を記録し、ローカルバックアップを更新する（§9.5）
7. 412 が返ったら §9.4 の競合手順へ。自動で全文を書き直さない

MCP サーバー内の書き込みは単一のキューで直列化し、同一プロセスからの並行 PUT が互いに 412 を誘発しないようにする。ただしブラウザー側の編集との競合は残るため、412 は通常起こりうる応答として扱う。

### 8.5 監査ログ

- Mac 上に追記専用ログ（JSON Lines）を残す。記録するのは: 時刻、ツール名、MCP クライアント識別、対象 revision（前 → 後）、mutationId、本文バイト数（前後）、結果コード（成功 / 412 / 409 / 検証失敗 等）、トークン ID
- **記録しないもの**: 本文平文、平文のハッシュ（短いメモではハッシュから内容を推測・照合される恐れがあるため）、VaultKey・秘密鍵・トークン平文、暗号文そのもの
- サーバー側の運用ログも §14 の既存方針（ルート、状態、時間、容量、エラーコード + 主体種別）を維持し、エージェント経由だからといって記録項目を増やさない
- ログの保持期間とローテーションは Mac 側の運用設定とする（既定: 90日）

## 9. 書き込み安全策

### 9.1 追記優先

- 既定の書き込みは `txt_append` のみとし、エージェントの通常運用（メモへの追記）はこれで完結させる
- 追記の適用規則: 共通モデルの**末尾が text ブロックならそのブロックの文字列末尾へ追加**する。末尾が media ブロックの場合は §8 の不変条件（メディアの前後には編集可能な text ブロックを確保する）に従い、末尾に新しい text ブロック（新規 ID）を追加してそこへ書く。既存ブロックの ID は変更しない
- 追記テキストの先頭の改行付与など、利用者の入力に対する暗黙の整形はしない（§3 の「trim や正規化をしない」原則をエージェントにも適用）。改行を入れたい場合は呼び出し側が `text` に含める

### 9.2 置換は承認制

- `txt_replace` / `txt_search_replace` は `confirm: true` を必須引数とし、MCP クライアント側でも利用者承認を挟む運用を前提とする（ツールの説明文に明記し、承認なしにエージェントが自律的に呼ばない契約にする）
- 置換前の完全一致を要求する: `txt_replace` は `expected_text` がブロック現行値と完全一致するときだけ実行する。一致しなければ現在のブロック内容を返して終了し、部分一致や曖昧な一致では書かない
- 削除を伴う置換（`new_text` が空、または現行の 50% 未満の長さになる置換）は、通常の置換より強い確認として扱い、応答に「削除を伴う」旨と差分を含めて承認を求める形にする
- サーバー側の防御は scope（`agent:write` がないトークンでは PUT 自体が 403）までとし、承認の有無は MCP 層の責務とする。サーバーは平文を見られないため、操作内容の審査は原理的にできない、という境界を明記する

### 9.3 メディア保護

- フェーズ2までの書き込みでは `referencedMediaIds` を変更しない。操作後のモデルの media 辞書と参照集合が操作前と一致しない書き込みは、MCP サーバー内で検証エラーとして拒否する（誤って fileKey を落としたモデルを保存すると添付が恒久的に読めなくなるため）
- 未知のブロック型・未知フィールドを含むモデルは、削除も再解釈もせず、そのまま保持して保存する（§8「未知の型・形式を削除して保存し直さない」の適用）

### 9.4 CAS 競合時と冪等性

- 412（ETag 不一致）を受けたら、**自動上書き・自動再試行・自動マージをしない**（§10.4 の Web の方針と一致）。MCP サーバーは最新版を再取得・復号し、次をツール応答としてエージェントへ返す:
  - 競合の事実と、ベース revision / 最新 revision
  - ベース → 最新 の差分（他者＝主にブラウザーの Kan 本人の編集）
  - 自分が適用しようとした操作の内容と、最新版に対してその操作がまだ意味を持つかの情報
  - エージェントはこの差分を利用者へ提示し、指示を受けてから新 ETag で再実行する
- 応答消失など結果不明の再送は §10.3 の規則どおり: 同じ mutationId + 同じペイロードなら冪等に成功扱い、同じ mutationId で異なるペイロードは 409。MCP サーバーは §8.4 手順5 の記録を使い、再暗号化せず記録済みペイロードをそのまま再送する
- ブラウザー側に未保存のローカル変更がある状態でエージェントが書くと、ブラウザー側の保存時に 412 となり Web の競合 UI（§4.6、§10.4）で解決する。これは既存の競合解決経路で処理でき、データは失われない。運用上の注意として、エージェントの書き込みは「読んでから書く」を同一ツール呼び出し内で行い、読み書きの間隔を最小化する

### 9.5 ローカルバックアップと復旧

サーバーは履歴を持たない（§2）ため、エージェントの誤書き込みへの保険は MCP サーバー側に置く。

- 書き込みが成功するたびに、**書き込み前の暗号文一式**（ETag、mutationId、nonce、ciphertext、referencedMediaIds）を Mac 上に保存する。平文では保存しない
- 保持は直近 20 世代または 7 日間のうち短い方。保存先はアプリ専用ディレクトリで、他の用途と混ぜない
- 復旧は専用操作 `txt-agent rollback`（CLI、MCP ツールにはしない）で行う: バックアップの暗号文を、現在の ETag に対する CAS 更新として新しい mutationId で再提示する。暗号文の再提示は AAD の encryptedRevision が変わるため、そのままでは検証を通らない点に注意し、復旧時は「バックアップを復号 → 現行 revision 向けに再暗号化」する手順とする（平文は Mac のメモリー内でのみ経由する）
- これは D1 Time Travel（運用者の復旧経路）を置き換えるものではなく、エージェント起因の事故専用の一次対応とする

## 10. 段階的実装計画

### フェーズ1: 読み取り専用

範囲: §4（鍵ラップ・登録）、§5（read トークン）、§6（スキーマ）、§7.1 と `GET /agent/envelope`、既存 `GET /document` のエージェント認可、MCP サーバーの `txt_status` / `txt_read`。

受け入れ条件:

- [ ] 登録フローが §4.3 の順序（step-up → 公開鍵登録 → フィンガープリント確認 → ラップ → カナリア試験 → active）でのみ完了し、途中離脱で active なエージェントが残らない
- [ ] エージェント鍵ラップの暗号テストベクトルを `packages/protocol` の既知入力/期待出力に追加し、Web 側の生成と MCP 側の解除が相互に一致する（§17.3 の既存観点の拡張）
- [ ] ラップ済み鍵、暗号文、カナリアのいずれかを1バイト改変すると復号が失敗し、空文書や部分的な平文が返らない
- [ ] 別アカウントのトークン、別エージェントのトークンでは envelope / document が引けない（404 で存在を漏らさない）
- [ ] 失効したトークンは次回リクエストから 401、失効したエージェントの全トークンが無効になる。`auth_epoch` を上げると全エージェントトークンが無効になる
- [ ] サーバーログと MCP 監査ログに平文・鍵・トークン平文が含まれないことをログ実物で確認する
- [ ] Bearer を Web 経路に使えないこと、Cookie をエージェント経路に使えないことを API テストで確認する

### フェーズ2: 書き込み

範囲: `agent:write` scope、`PUT /document` のエージェント認可、MCP の `txt_append` / `txt_replace` / `txt_search_replace`、§9 の安全策一式、ローカルバックアップ。

受け入れ条件:

- [ ] 追記が §8 のブロック規則（ID 維持、末尾 media の場合の新ブロック追加、末尾 LF・空行の保持）を満たし、Web で開いて往復保存してもモデルが変わらない
- [ ] ブラウザー編集中の並行保存を再現し、エージェント側が 412 で停止して差分を返し、サーバーの内容がどちらの書き込みでも失われない
- [ ] 同じ mutationId の同ペイロード再送で revision が二重に進まない。異ペイロード再送は 409
- [ ] media を含む文書への追記・置換後、すべての添付が Web で復号表示でき、`referencedMediaIds` が不変である
- [ ] `expected_text` 不一致の置換、複数一致の全文置換が、書き込みを行わずに終わる
- [ ] ローカルバックアップからの rollback で書き込み前の内容に戻ることを、実データ相当の fixture で確認する
- [ ] write scope のないトークンでの PUT が 403 になる

### フェーズ3: 管理 UI の完成とローテーション

範囲: セキュリティ設定でのエージェント一覧・失効・トークン期限表示（§4.6 のセキュリティ設定の拡張）、鍵署名によるトークン更新（§5.3）、VaultKey ローテーション手順。

VaultKey ローテーションの設計スケッチ:

1. 利用者が Web でローテーションを開始する（step-up 必須）。ブラウザーは新 VaultKey を生成し、現在の文書を新鍵で再暗号化して CAS 保存する（key_version を上げる）
2. 現在使用中のパスキーと復旧キーについては、その場で新 VaultKey のラップを作り直す（復旧キーは新 RecoverySeed を発行し、保存確認を必須とする。§7.2 の復旧確定と同型）
3. その場で PRF を得られない他のパスキー・エージェントについては、移行ラップ `AES-GCM(旧VaultKey由来KEK, 新VaultKey)` をサーバーに置く。各入口は次回解除時に旧 VaultKey で移行ラップを開き、自分の入口用の正式ラップへ置換してから移行ラップを消す。全入口の移行が済むか、利用者が残りの入口を失効させた時点で移行ラップを完全削除する
4. 移行期間中も旧 VaultKey は有効である（= 侵害対応としてのローテーションの効果は移行完了時点で初めて確定する）ことを UI で明示する

受け入れ条件:

- [ ] エージェント失効操作が Web から行え、失効直後に対象 MCP からの読み書きが両方止まる
- [ ] トークンの鍵署名更新が、旧トークンの失効と原子的に行われ、署名検証失敗では新トークンが発行されない
- [ ] ローテーション完了後、旧 VaultKey で現在の暗号文が復号できないこと、移行ラップが残っていないことを確認する
- [ ] ローテーション途中で中断しても、既存の入口のいずれかで必ず開ける状態が保たれる（読めない active 文書を作らない。§17.3 の既存原則）

## 12. 未決事項（Kan の判断が必要な点）

1. **提供範囲**: エージェント接続を全アカウント向け機能にするか、当面は Kan のアカウントのみ（フラグ制御）にするか。txt は一般公開サービスであり、サポートと悪用対策の負担が変わる
2. **トークン更新の運用**: フェーズ1〜2 の「期限切れ時は Web から再発行（手作業）」で開始してよいか。30日ごとの手作業を許容するか、フェーズを前倒して鍵署名更新を入れるか
3. **書き込み承認の粒度**: 追記は承認なし、置換は承認あり、という本書の線引きでよいか。追記にも毎回承認を求めるかは、使い勝手と安全性のトレードオフ
4. **秘密鍵の保管レベル**: フェーズ1 は Keychain（ACL 付き）で開始し、Secure Enclave 化（CryptoKit ヘルパーの追加実装が必要）はフェーズ3以降でよいか
5. **メディア読み取りの範囲**: フェーズ1 の `txt_read` はメディアをプレースホルダー表示とするが、画像の内容をエージェントへ渡す（MCP が復号して画像データとして返す）機能を入れるか、入れるとすればどのフェーズか
6. **エージェント登録数の上限**: アカウントあたりの active エージェント上限（例: 5件）を設けるか
7. **ローカルバックアップの保持**: §9.5 の「直近20世代または7日間」が妥当か。平文ではなく暗号文とはいえ、Mac 上に旧版が残ることの是非
8. **MCP の待ち受け形態**: launchd 常駐 + Tailscale bind で確定してよいか（都度起動型にすると Muse からの接続体験が変わる）
